## 本人承認と目的

オーナーは「提案にとどまらず自動で気づいたことはサイクルを回して改善」「グロースとSEO担当も繋げて良い」「自動で日々サイトを良くして」と明示した。この指示を `OWNER-20261102-GROWTH-SEO` として記録する。

この承認により、FRAMEPACTの**既存公開ページの通常のSEO・問い合わせ導線改善**は、分析、相互レビュー、よっしーAIの既存判断基準確認、PR作成、検証、merge、本番確認、効果確認まで進める。範囲内の変更を毎回本人確認で止めない。役割追加時に定めた一律の「提案のみ・公開禁止」はこの範囲について更新し、その他の作業には従来どおり適用する。AIが本人承認を生成する仕組みではない。

目的は、承認済みサービスに合う相談へ至る経路を改善すること。順位、PV、記事数、変更件数だけを成果にしない。本人の制作時間を増やす低単価受託へ誘導せず、既存の事業判断基準に従う。

## 対象と担当

対象は `https://framepact.jp` の既存公開ページ、および対応する `LifeifCreater/ai-video-business` の実装。承認済みの事実を使った見出し・説明の明確化、title・description、内部リンク、既存CTAの文言や配置、アクセシビリティ、モバイル表示、客観的に確認できるリンク・canonical・sitemap等の不具合を扱う。URL移行、大規模な全面改稿、コンテンツ削除は含めない。

| 担当 | このサイクルでの責任 |
|---|---|
| 統括秘書 | 日次ID・入力版・競合を確認し、担当を割り当て、PRから本番確認とPrivate記録まで完了させる |
| グロース・CRO | データ品質、相談までの導線、主仮説、主指標・分母、副作用、観測期間を設計し、SEO案の事業効果をレビューする |
| SEO | 検索意図、既存ページの役割、見出し・内部リンク・技術SEOを点検し、グロース案が検索流入や内容の正確さを損なわないかレビューする |
| よっしーAI | 正本と既存判断基準に照らし、適切な相談、本人実働、再利用性、品質に適合するか確認する |

17役を常駐17AIと扱わない。必要な少数担当だけが実作業を行い、実行者・時刻・入力SHA・成果物・レビュー対象SHAを記録する。利用可能なら実装者と別の実行者による独立レビューを優先する。別エージェント機能がない場合も、低リスクの許可範囲では実装後にグロース・SEO・よっしーAIの確認観点を分けた第二パスを実行し、`executionMode=same_actor_separate_passes` と記録して進める。同じアシスタントの役割切替を独立レビューとは呼ばない。高影響の変更や検証できない差分だけを保留し、利用できない独立機能だけを理由に通常改善全体を停止しない。

営業送信・顧客連絡、価格・値引き・納期・成果の約束、未承認の実績や顧客情報、契約・法務、支出・広告・有料サービス、認証・権限変更、フォーム送信先や計測アカウント・同意設定、金融資産、他の事業資産は対象外。承認待ちの編集部原稿・企画・投稿状態を変更しない。このサイクル自身の権限や検証条件を弱める変更も対象外。

| 用途 | ブランチ | パス |
|---|---|---|
| 入力manifest | `data/growth-seo` | `automation/growth-seo/latest.json` |
| 分割レポート | `data/growth-seo` | manifestで指定されたパス |
| ロック・実行状態 | `state/growth-seo` | `automation/growth-seo/state.json` |

| 実験・評価履歴 | `state/growth-seo` | `automation/growth-seo/experiments/` |

最初に入力ブランチのrefをcommit SHAへ解決する。manifestと必要なレポートは同じSHAで読み、取得中の更新が混ざらないようにする。保存形式は `report_parts_v1`。各reportの `parts` にあるパスから分割JSONを読み、raw bytesのSHA256・行数・report識別をmanifestと照合してから使う。取得から36時間を超えるsnapshot、欠けたレポート、取得失敗、上限制限・匿名化・threshold等のqualityを確認する。データ欠損を0へ補完しない。GSCの `quality.complete=false` は通常のtop rows仕様でも生じるため、それだけで全分析を止めない。GA4がokでも全行が除外された場合は観測値がない状態として扱い、0件と解釈しない。

主比較は直近28日とその前28日。直近7日とその前7日は参考とする。GA4のページ・ランディングページ・問い合わせイベント、GSCのページ・検索クエリ・ページ×クエリを用途に応じて読む。GA4の日本・本番host、GSCの日本・Web・本番hostの対象範囲と各ソースの日付定義を保持し、合算して単一の顧客数としない。実際の期間・タイムゾーン・確定境界はmanifestと各レポートを優先し、未確定日の数値で成果を断定しない。

最大1000行のレポートや匿名化で省略されるクエリは全母集団ではない。行がないことを0件と扱わず、page合計とquery合計の差を欠陥と決めつけない。CTAクリック、フォーム到達、正常送信、有効相談、商談、受注は別指標。GA4で取得できない有効相談や売上は未取得のまま残す。

## 日次の進め方

データ取得は03:30、改善点検は07:00頃、通常の結果共有は09:00朝会へ集約する（すべてJST）。実際の実行時刻・成功はジョブ履歴で確認し、予定を実績として扱わない。文書の存在だけで予約済み・稼働済みと判断せず、登録済みタスクと実行証拠を確認する。

1. **状態を確保する。** JST日付から `GROWTH-YYYY-MM-DD` を作り、Private状態を読み、取得したstateブランチSHAを前提にロックを確保する。既に当日実行・PR・mergeがあれば再開または観測に進み、同じ変更を作り直さない。
2. **既存の変更を評価する。** 7・14・28日の評価期限、本番確認待ち、失敗・途中状態を先に扱う。公開main、開いているPR、既存編集部の状態・lockを読み、同じファイルやURLの競合があれば新規変更を保留する。
3. **根拠から一つ選ぶ。** 入力品質と現在の実装を確認し、相談への影響と検証可能性で優先順位を決める。通常変更は1日最大1件。1件は一つの仮説または共通欠陥を指し、同じ欠陥を直す複数ファイルは一件として扱う。毎日改稿する必要はなく、観測継続・変更なしも正常な結果。
4. **両者で相互レビューする。** グロースはSEO案の相談経路・測定方法を、SEOはグロース案の検索意図・技術影響を確認する。よっしーAIは既存事業基準を確認する。必要な内部修正は最大2巡。未解決事項は保留するが、無関係な許可済み作業は進める。
5. **PRで実装・検証する。** 変更前の基準値または再現手順、対象URL、仮説、主指標と分母、副作用監視、観測期間、撤回条件をPrivate実験票へ残す。公開PRには変更内容・公開情報から分かる理由・確認結果だけを書く。独立レビューを優先し、利用できない場合は低リスク範囲に限って実装後の別パスで最終差分を確認する。実際のレビュー方法を記録し、該当テストと必須CIがすべて現在のhead SHAで成功したことを確認する。
6. **mergeして本番を確認する。** 最後にhead SHA・main・競合・レビュー状態を再取得し、差分が変わっていれば検証し直す。直接main pushやforce更新は行わず、既存のPR・デプロイ経路で反映する。変更したページの表示、リンク、CTA遷移、必要に応じてcanonical・モバイル表示を本番で確認する。実問い合わせ・顧客へのメッセージを発生させる試験送信はしない。
7. **Privateに結果を残す。** PR・commit・本番確認URL・確認時刻・担当別レビュー・次の評価日を保存する。merge済みでも反映確認できなければ本番確認待ちとする。通常通知を追加せず、`latest.md` に朝会向け結果をまとめる。

## 実験の観測と撤回

同じURL・同じ仮説は原則14日観測してから次の変更を行う。客観的に再現した不具合や、自分の変更による確定した回帰の撤回は例外とし、その理由を記録する。通常の1日1件制限を根拠なく増やさない。

7日では方向と計測品質を確認する。14・28日では、実装後のデータが確定した期間と、曜日構成・母数・流入区分をそろえた変更前期間を比較する。入力の移動28日窓に実装前後が混在する間は、その値だけを変更効果とみなさない。必要な期間がまだ取得できなければ観測を延長する。

判断は `improved / unchanged / regressed / inconclusive` とし、確認できる観測結果と因果の仮説を分ける。小標本、同時施策、季節性、検索変動を無視して「改善によって問い合わせが増えた」と断定しない。事前に決めた主指標・分母・実務上の判断基準・副作用を使用し、都合のよい指標へ後から置き換えない。

本番のリンク切れ、フォーム導線破損、表示崩れ、誤ったnoindex/canonical等、自分の変更による技術回帰が確認できた場合は、元のPR・commitに限定して撤回PRを作り、検証・merge・本番再確認まで進める。同時に入った他者の変更を上書きしない。一日の指標変動や単なる「未改善」は自動撤回の根拠にしない。

## 重複実行と失敗の扱い

state更新は既存runtimeのスキーマ・書き込み手順に従い、読み取ったブランチSHAからのfast-forwardのみ許可する。競合したら再読込し、当日の既存実行・lock・PR・commitと照合する。force updateで勝たない。期限切れlockも直ちに捨てず、PRや本番に変更が残っていないか確認してから再開する。ロックが確保できないままPublicへ書き込まない。

記録には日次ID、実行者、入力SHA、public main SHA、開始・更新時刻、状態、変更理由、PR・commit、レビューの対象SHA、テスト、本番検証、失敗理由、次回評価を含める。実験記録には対象URL、仮説、変更前根拠、主指標・分母・期間・quality、ガードレール、撤回方法を含める。実際のJSONフィールドと状態値はPrivate runtime実装を正本とし、ここにある概念名を別の非互換スキーマとして作らない。

データがない日は待機するか、実画面・コードから客観的に確認できる技術不具合だけを扱う。GitHub書き込み権限、Private保存、必要な確認パス、CI、本番確認が使えない場合は成功としない。許可のない経路へ迂回せず、可能なPrivate状態に失敗・待機理由を残して朝会へ伝える。Privateへの書き込みも失敗した場合は、非公開データを出さずに既存の実行結果へ障害だけ記録する。

範囲外の判断が必要になったときだけ、完成した差分・理由・必要な判断をまとめて本人へ確認する。既存公開ページの通常改善について、毎回の許可待ちを新設しない。
